FPGA board simulator

This page covers fpga-sim, the app I developed for WPI’s digital circuits course to let students run synthesizable Verilog code on-screen on almost any computer. It is available on GitHub for download.

Background

As a sophomore at WPI, I took the course Introduction to Digital Circuit Design (ECE2029) and enjoyed it a lot. A big part of it was using Verilog to program FPGA devkits; being able to write code which turned into an accurate circuit was amazing to me.

The next year, I was a TA for the course. That year, they did not use FPGAs anymore for cost reasons, only teaching Verilog via testbench simulations. I thought that removing the experience of writing code that you would physically interact with via the board was a big downgrade. Also, the students still had to run their testbenches with Vivado; of course, Vivado had been necessary when FPGAs were used, but the new version of the class only used a tiny part of it. The large download size and lack of Mac support, among other issues, added unnecessary friction to the class.

In winter break of my senior year, I developed an app in the hopes of improving the course, which I then deployed as a TA. My software emulates the experience of the FPGA devkits, running synthesizable code on a “virtual board.” Using Verilator in a container, users’ code is turned into a fast C++ model, linked with a driver program into an executable, and run at a fixed speed, receiving input states from a GUI window and sending its output state back to be rendered. It also uses Verilator to run testbenches much more quickly than Vivado does.

The app is cross-platform, with full support for Mac, Windows, and Linux, and has low performance requirements. It uses PySide6 (Qt) for the boards, so the GUI is highly consistent across operating systems. VSCode is recommended as the associated IDE to write your source code in, and it supports automatically opening testbench waveforms with VaporView (a VSCode extension), GTKWave, or Surfer.

On course staff, I overhauled most of the class’s lab assignments to integrate the simulator and held extensive office hours. The software was installed by at least 50 lab pairs/groups from our class of about 120 students.

Virtual boards

The FPGA simulation feature supports multiple “virtual boards” with different layouts and I/O. At the time of the course, the software supported one virtual board, directly based on the devkit formerly used for the class.

Classic board

An example of a program running on my first board, which is based on the old class’s devkits, is shown below. At the time of the course, this was the only supported board, so I later named it “classic.”

The Verilog program shown running is a calculator design similar to one students made in one of the labs I developed for the course. The app selects light or dark mode based on system settings.

Notice the fade effect when the numbers are changing. This is because the segmented display’s inputs are a number pattern and a digit select code, so it must constantly cycle to show more than one thing at a time. See below a slowed-down rendition of how numbers are shown:

With the real-world display, the clock speed is on the order of megahertz. Because the digits switch extremely fast and take a moment to fade off, this looks like a persistent and bright “0312” to the human eye. The software’s clock is much slower (60 Hz), so I apply a greatly exaggerated fade effect whenever a segment switches off to eliminate flickering.

Additional boards

After the term, I continued working on the project and released a second edition of the software. This update removed the hard-coding of the single devkit from the server code, now using some light code generation to create a C++ driver compatible with any model the user’s code produces; therefore, to add a new board, a user just needs to write a small new Python program to run on the client side and add a line to a toml config file.

Using this new system, I made multiple new boards and included them with the program. Shown below are two of them:

  • A four-function calculator with a four-digit dot-matrix display. This takes a display programmed similarly to the seven-segment and creates a specific “device” to use it.
  • A board for a game inspired by old LCD handhelds. In this game, the user moves a bucket to catch apples. This uses a new widget I made to hide and show elements of an SVG.

The components of my “official” boards are all designed to be reused in new code and my hope is that an ambitious instructor using the program will make more of them to provide interesting bespoke labs for students. The app supports adding new boards in a separate file from the main board configuration, to make it harder for students to accidentally break the program when adding their teachers’ extensions.

Defining a new board using existing components would be fairly easy for someone with moderate programming skills. The included boards all subclass board__base.py, which does basically all of the repetitive setup, and each only takes about 70 to 150 lines of simple Python code. The widgets I’ve made so far, which can be imported and reused for new boards, include:

  • Sticky and non-sticky buttons
  • Switches (dressed-up checkboxes)
  • Seven-segment display groups with any number of digits
  • Dot-matrix display groups with any number of digits, any vertical or horizontal resolution, and any size or spacing of the inner “pixels” and groups of pixels
  • The SVG renderer used for the apple game board

Supporting novice users

One aspect of the course I kept in mind while developing the app is that ECE2029 is mostly taken by first-year ECE students, and has no programming prerequisites. Therefore, the app’s instructions walk users through the process quite thoroughly. For example they explain how to check your computer’s CPU architecture, which is needed for many of the required downloads. It is also very specific about the steps taken in the terminal.

In this vein, the program itself has some helpful features such as checking that the user-provided code’s ports match the required ones and printing helpful errors. For the classic board specifically, I implemented a list of aliases matching my names to the original devkit’s constraint file:

    * Missing input "RB:1".
    Suggestion: rename "btnR" to "RB"
    * Missing input "CB:1".
    Suggestion: rename "btnC" to "CB"
    * Missing output "segment:7".
    Suggestion: rename "seg" to "segment"
    * Missing output "anode:4".
    Suggestion: rename "an" to "anode"

Another piece I worked on to help students narrow down issues is processing of Verilator’s error messages. When my program receives raw error printout, it trims it down, removing some info irrelevant to a regular user such as Makefile line numbers and deleting suggestions to use always_latch (bad advice for students in almost any scenario). It also converts the filepaths to be clickable on the user’s terminals and adds some color to the output.

Raw error output:

%Warning-LATCH: user_inputs/top.v:168:1: Latch inferred for signal 'top.current_num' (not all control paths of combinational always assign a value)
                                       : ... Suggest use of always_latch for intentional latches
  168 | always_comb begin
      | ^~~~~~~~~~~
                ... For warning description see https://verilator.org/warn/LATCH?v=5.046
                ... Use "/* verilator lint_off LATCH */" and lint_on around source to disable this message.
%Error: Exiting due to 1 warning(s)
make: *** [Makefile:75: generate_code] Error 1

Complete user-facing printout:

Warning-LATCH: verilog/live_sim/realadd/top.v:168:1: Latch inferred for signal 'top.current_num' (not all control paths of combinational always assign a value)

168 | always_comb begin
    | ^~~~~~~~~~~

Elaboration of designs is also prevented if there is a linting error. This avoids situations such as Verilator raising a NULLPORT error on a module with a trailing comma during linting, but then raising a totally contradictory PINMISSING error in the following “doomed” build.
